Abstract

Daleel is a comprehensive fleet management system designed to address the challenges of monitoring and controlling fleets consisting of hundreds or even thousands of vehicles of various types, including cars, trucks, and commercial vehicles. The system provides real-time tracking, detailed historical data analysis, and advanced driver performance evaluation to support efficient, secure, and data-driven fleet operations.

The core functionality of Daleel includes live vehicle location tracking, trip management, and route history recording. The system stores and analyzes critical driving data such as average speed, maximum speed, driving duration, stop intervals, and trip frequency. These features enable fleet operators to monitor driver behavior, improve safety, reduce operational costs, and enhance overall fleet efficiency.

In addition to tracking and analytics, Daleel focuses on system scalability and reliability, making it suitable for large-scale deployments. The architecture is designed to support continuous operation, high data throughput, and long-term data storage, allowing fleet managers to review historical performance and generate actionable insights.

This graduation project presents a complete end-to-end solution, covering both hardware and software aspects of the system. On the hardware side, the project discusses the design of the in-vehicle tracking unit, including positioning, communication, power management, and sensor integration. On the software side, it covers the backend architecture, data processing, database design, communication protocols, and user interfaces for monitoring and analysis.

Furthermore, the project explores additional features such as maintenance monitoring, trip reporting, alert generation, and system security considerations. By integrating embedded systems, communication technologies, and software engineering principles, Daleel aims to provide a practical, scalable, and cost-effective fleet management solution suitable for real-world applications.

2.1 Introduction

This chapter presents the hardware design of the proposed embedded tracking and sensing system. The system integrates sensing, positioning, and wireless communication capabilities using modern embedded modules. The design focuses on modularity, low power consumption, and reliable communication between subsystems.

The hardware platform is built around the ESP32-S3 microcontroller and integrates three main peripheral modules: a motion sensing unit (MPU6050), a GSM communication module (SIM800L V2), and a GPS positioning module (u-blox NEO-8M). These components work together to collect environmental and positional data and transmit it remotely.

It is important to note that the printed circuit board (PCB) presented in this work represents a future implementation design. The PCB was designed and simulated using electronic design software but has not yet been fabricated or physically tested. The design serves as a proof of concept and demonstrates the feasibility of integrating all components into a compact embedded system.

2.5mpu6050

fig2.1 : mpu6050

2.5.1Overview

The MPU-6050™ parts are the world’s first MotionTracking devices designed for the low power, low cost, and high-performance requirements of smartphones, tablets and wearable sensors.

The MPU-6050 incorporates InvenSense’s MotionFusion™ and run-time calibration firmware that enables manufacturers to eliminate the costly and complex selection, qualification, and system level integration of discrete devices in motion-enabled products, guaranteeing that sensor fusion algorithms and calibration procedures deliver optimal performance for consumers.

The MPU-6050 devices combine a 3-axis gyroscope and a 3-axis accelerometer on the same silicon die, together with an onboard Digital Motion Processor™ (DMP™), which processes complex 6-axis MotionFusion algorithms. The device can access external magnetometers or other sensors through an auxiliary master I²C bus, allowing the devices to gather a full set of sensor data without intervention from the system processor. The devices are offered in a 4 × 4 × 0.9 mm QFN package.

The InvenSense MotionApps™ Platform that comes with the MPU-6050 abstracts motion-based complexities, offloads sensor management from the operating system, and provides a structured set of APIs for application development.

For precision tracking of both fast and slow motions, the parts feature a user-programmable gyro full-scale range of ±250, ±500, ±1000, and ±2000 °/sec (dps), and a user-programmable accelerometer full-scale range of ±2g, ±4g, ±8g, and ±16g. Additional features include an embedded temperature sensor and an on-chip oscillator with ±1% variation over the operating temperature range.

2.5.2 Communication Protocol: The I2C Interface

The MPU-6050 utilizes the I2C (Inter-Integrated Circuit) bus for communication, which is a synchronous, multi-master, multi-slave, packet-switched, single-ended, serial communication bus. In the context of our graduation project, the ESP32 acts as the Master, and the MPU-6050 acts as the Slave.

2.5.3 Device Addressing

The MPU-6050 has a flexible 7-bit I2C address. The default address is typically 0x68. However, the device features an AD0 pin (Address Select) which allows the user to change the LSB (Least Significant Bit) of the address:

  • If AD0 is Logic Low (GND): The address is 1101000 (0x68).
  • If AD0 is Logic High (3.3V): The address is 1101001 (0x69).

    This feature is crucial for projects requiring two MPU-6050 sensors on the same bus without address conflicts.

2.5.4 The Auxiliary I2C Bus

One unique feature of the MPU-6050 is its Auxiliary I2C Master Bus. This allows the MPU-6050 to act as a master to other sensors, such as an external magnetometer (e.g., HMC5883L). The MPU-6050 can read data directly from the magnetometer and pass the combined 9-axis data to the ESP32, significantly reducing the wiring complexity and processing overhead on our main controller.

2.5.5 ESP32 Hardware Integration and Pinout

Integrating the MPU-6050 with the ESP32 requires careful consideration of voltage levels and pull-up resistors. While the MPU-6050 chip itself is a 3.3V device, many modules (like the GY-521) include a voltage regulator, allowing them to be powered by 5V. However, the logic lines (SDA/SCL) should always stay at 3.3V to match the ESP32 GPIO tolerance.

2.5.9 Handling Sensor Noise and Calibration

Raw data from the MPU-6050 is rarely perfect. Even when sitting still, the gyroscope will show a small non-zero value known as Zero-G Offset or Drift. To solve this for the graduation project, we implemented a calibration routine in the firmware that records the average error over 1,000 readings at startup and subtracts this "bias" from all subsequent measurements.

2.6 u-blox NEO-8M GNSS Module

2.6.1 Overview

The NEO-8M is a high-performance concurrent GNSS (Global Navigation Satellite System) module that builds upon the legacy of the NEO-6 series. Unlike its predecessors, which often tracked only one satellite system at a time, the NEO-8M utilizes the u-blox M8 engine to receive signals from up to three GNSS systems concurrently. This results in superior positioning accuracy, especially in challenging environments like "urban canyons" (high-rise cities) or dense foliage.

2.9.2Core Improvements over NEO-6M

  • 72-Channel Engine: Compared to the 50 channels of the 6M, allowing for more satellite locks.
  • Update Rate: Capable of up to 10 Hz (10 location updates per second), whereas the 6M typically caps at 5 Hz.
  • Sensitivity: Tracking sensitivity is improved to –167 dBm, allowing for a "warm start" in as little as 1 second.
  • Anti-Jamming: Includes an extra onboard SAW filter and a Low Noise Amplifier (LNA) to protect against signal interference.

2.6.6 Understanding Start Modes: Cold, Warm, and Hot Start

A significant portion of a GPS tracker's efficiency depends on its "Time to First Fix" (TTFF). The NEO-8M operates in three distinct states based on the data it has stored in its internal Battery-Backed RAM (BBR).

2.6.7 Cold Start (Standard Initial Boot)

A Cold Start occurs when the receiver has no valid data: no position, no accurate time, and no Almanac or Ephemeris data. This usually happens when the device is new, factory reset, or has been powered off for weeks without a backup battery.

  • Process: The receiver must search all possible frequencies to find satellites. It then downloads the Almanac (orbit data for all satellites) and the Ephemeris (precise orbit for specific satellites).
  • TTFF: Typically 26 to 60 seconds in clear sky.

2.6.8Warm Start (Stored Almanac)

A Warm Start happens when the device has been off for more than 4 hours but has a working backup battery. It remembers the Almanac and its last known position/time but the Ephemeris data (valid for ~4 hours) has expired.

  • TTFF: Typically 5 to 15 seconds.

2.6.9 Hot Start (Instant Fix)

A Hot Start is the ideal state for a tracker. The device was recently active (less than 4 hours ago). It has valid position, time, Almanac, and Ephemeris data.

  • TTFF: Typically 1 to 2 seconds.

2.6.10Performance Tuning: Concurrent GNSS Optimization

The NEO-8M's "M" stands for "Multi-constellation." To make your tracker more accurate in cities, you should tune it to listen to multiple satellite systems simultaneously.

2.6.11 Enabling Galileo and GLONASS

By default, some modules only search for GPS. Tuning the module via the UBX protocol allows it to use:

  • GPS (USA): Reliable global coverage.
  • GLONASS (Russia): Better coverage in northern latitudes.
  • Galileo (Europe): High precision for civilian use.

2.6.12 Tuning the Navigation Update Rate

For a high-speed vehicle tracker, 1 Hz (one update per second) might be too slow. The NEO-8M can be tuned to 5 Hz or 10 Hz.

  • 1 Hz: Best for battery life (lower CPU load).
  • 10 Hz: Best for high-speed tracking or racing drones.

2.6.13 Advanced Implementation: Software Logic for Fast Fix

To ensure your tracker always starts as "Hot" as possible, we use a code logic that checks if the backup battery is maintaining the data.

C++

#include <TinyGPS++.h>
#include <HardwareSerial.h>

TinyGPSPlus gps;
HardwareSerial SerialGPS(2); 

// Configuration: Increase rate to 5Hz (200ms)
byte packet[] = {0xB5, 0x62, 0x06, 0x08, 0x06, 0x00, 0xC8, 0x00, 0x01, 0x00, 0x01, 0x00, 0xDE, 0x6A};

void setup() {
  Serial.begin(115200);
  SerialGPS.begin(9600, SERIAL_8N1, 16, 17);

  Serial.println("Optimizing NEO-8M Performance...");
  
  // Send UBX command to change rate to 5Hz
  for (int i = 0; i < sizeof(packet); i++) {
    SerialGPS.write(packet[i]);
  }
  Serial.println("Update rate set to 5Hz (200ms intervals).");
}

void loop() {
  while (SerialGPS.available() > 0) {
    if (gps.encode(SerialGPS.read())) {
      if (gps.location.isUpdated()) {
        Serial.print("Sats: "); Serial.println(gps.satellites.value());
        Serial.print("HDOP (Precision): "); Serial.println(gps.hdop.hdop());
        // High Precision is HDOP < 1.5
      }
    }
  }
}

2.7.7Troubleshooting Network Registration

If the "NET" LED on the SIM800L v2 is flashing rapidly (once per second), it means it cannot find the network.

  1. Power: Ensure the 5V source can provide 2 Amps.
  1. Antenna: Ensure the IPEX antenna is firmly connected and not touching metal.
  1. SIM Compatibility: In 2026, ensure your local carrier still supports 2G (GSM). If not, a 4G module (SIM7600) would be required.

2.7.8GPRS Protocol and Internet Connectivity

While SMS is reliable for emergency alerts, it is expensive and slow for continuous tracking. By utilizing the GPRS capabilities of the SIM800L v2, the device can maintain a persistent connection to a remote server using the Internet Protocol (IP) suite.

2.7.9What is an APN (Access Point Name)?

The APN is the "gateway" between the mobile network and the public internet. Think of it as the configuration that tells the SIM800L which path to take to reach the web. Without the correct APN, the mobile carrier will reject the module's request for an IP address.

An APN consists of three main components:

  1. Network Identifier: Identifies the external network (e.g., internet).
  1. Operator Identifier: (Optional) Identifies the specific carrier's domain.

void uploadData(float lat, float lon) {
  // Start HTTP Service
  SerialSIM.println("AT+HTTPINIT"); 
  delay(100);
  
  // Set HTTP Parameters (The URL of your tracking server)
  SerialSIM.print("AT+HTTPPARA=\"URL\",\"http://your-server.com/update?lat=");
  SerialSIM.print(lat, 6);
  SerialSIM.print("&lon=");
  SerialSIM.print(lon, 6);
  SerialSIM.println("\"");
  delay(100);

  // Set Action to GET or POST
  SerialSIM.println("AT+HTTPACTION=0"); // 0 = GET, 1 = POST
  delay(3000); // Wait for server response

  // Read Server Response
  SerialSIM.println("AT+HTTPREAD");
  delay(100);

  // Terminate HTTP Service to save power
  SerialSIM.println("AT+HTTPTERM");
}

Chapter 3: Firmware Architecture and Real-Time Systems

3.1 The Shift to Real-Time Operating Systems (RTOS)

3.1.1 Limitations of the Standard "Super-Loop" Architecture

The "Super-Loop" architecture—commonly referred to as the void loop() structure in the Arduino ecosystem—is the most fundamental way to program a microcontroller. In this model, every instruction is executed sequentially. While this is sufficient for simple projects like blinking an LED or reading a single temperature sensor, it presents significant structural flaws when applied to a multi-peripheral system like a GPS Tracker.

https://www.circuitstate.com/tutorials/how-to-write-parallel-multitasking-applications-for-esp32-using-freertos-arduino/

Figure 3.1: Sequential vs. Multi-threaded Flowchart

1. The Blocking Delay Problem

The most severe limitation of the Super-Loop is its synchronous nature. In a GPS tracker, the SIM800L module often requires several seconds to attach to a GPRS network or wait for an HTTP response. If the code uses a delay() or even a "blocking" while() loop to wait for the modem, the entire CPU stops.

  • Impact on GPS: During those 5–10 seconds of waiting for the GSM network, the GPS module continues to stream NMEA sentences at 9600 baud. Since the CPU is "blocked" and not reading the Serial buffer, the buffer overflows.
  • Result: The system loses critical location data, and the GPS fix becomes "stale" or corrupted.

https://deepbluembedded.com/uart-pic-microcontroller-tutorial/

Figure 3.2: Serial Buffer Overflow Diagram

2. Lack of True Concurrency

In a 100-page book, it is important to distinguish between "Parallelism" and "Concurrency." A Super-Loop can only do one thing at a time. If the code is busy calculating a checksum for a GPS string, it cannot simultaneously check if a "Stop" command has been received via SMS.

In our project, we have three high-speed operations happening:

  1. GPS Stream: Constant incoming data (UART1).
  1. GSM Communication: Frequent AT command handshakes (UART2).
  1. Motion Monitoring: Real-time interrupt triggers from the MPU-6050.

In a Super-Loop, these must "wait their turn." If the GSM task takes too long, the Motion sensor might miss a vibration event, or the GPS might lose its synchronization with the satellites.

3. Jitter and Unpredictable Timing

"Jitter" refers to the irregularity in the timing of code execution. Because different branches of an if/else statement take different amounts of time to run, the "sampling rate" of the sensors in a Super-Loop is never constant.

For a graduation project, this is seen as "non-deterministic" behavior. If we want to send data every exactly 10,000ms, a Super-Loop might actually send it at 10,500ms or 11,000ms depending on how long the GSM response took. This makes the data analysis in Chapter 5 much harder to justify.

4. Poor Resource Utilization (The ESP32-S3 Waste)

The ESP32-S3 is a dual-core processor. A standard Super-Loop only runs on Core 1, leaving Core 0 completely idle. In a professional engineering context, using only 50% of the available silicon while the system struggles with timing is considered poor design. The Super-Loop architecture has no native way to "assign" tasks to the other core, effectively wasting the high-performance capabilities of the S3 chip.

https://linuxhint.com/what-chip-esp32/

Figure 3.3: ESP32 Dual-Core Block Diagram

3.1.2 Introduction to FreeRTOS on ESP32-S3

The transition from a basic Arduino sketch to a Real-Time Operating System (RTOS) represents a shift from procedural programming to event-driven multitasking. For the Nano Tracker project, FreeRTOS (Real-Time Operating System) was selected as the kernel. It is an open-source, deterministic operating system designed specifically for microcontrollers with limited resources but high-reliability requirements.

1. The Core Philosophy: The Scheduler

https://medium.com/embedworld/freertos-co-routines-lightweight-multitasking-on-tiny-mcus-4150a8258c3a

Figure 3.4: FreeRTOS Scheduler Timeline

The most critical component of FreeRTOS is the Scheduler. In a standard loop, the programmer must manually manage when every function runs. In FreeRTOS, the Scheduler acts as a "manager." It maintains a list of all active Tasks (GPS, GSM, Power Management) and uses a Preemptive Priority-Based algorithm to decide which task gets to use the CPU at any given microsecond.

  • Preemption: If the GPS task is mid-calculation and the GSM task receives an emergency SMS, the Scheduler can "preempt" (pause) the GPS task instantly to handle the higher-priority GSM event.
  • Determinism: FreeRTOS guarantees that tasks will respond to interrupts within a specific, predictable timeframe. This is vital for our tracker to ensure no GPS coordinate pulse is ever missed.

2. Dual-Core Symmetric Multiprocessing (SMP)

https://docs.espressif.com/projects/esp-idf/en/v4.2.5/esp32/api-guides/freertos-smp.html

Figure 3.5: ESP32 Core Affinity Diagram

The ESP32-S3 is a Dual-Core processor, containing two Xtensa® 32-bit LX7 cores. While standard Arduino only uses one core, FreeRTOS on the ESP32-S3 allows for Symmetric Multiprocessing.

In this project, we utilize the xTaskCreatePinnedToCore() function. This is a specialized version of the standard task creation that allows us to "pin" a task to a specific processor.

  • Protocol CPU (Core 0): Dedicated to the SIM800L stack. Since GSM/GPRS involves long "Wait" times for network handshakes, Core 0 handles these delays without affecting the rest of the system.
  • Application CPU (Core 1): Dedicated to high-speed sensing. Core 1 runs the TinyGPS++ parsing and the MPU-6050 vibration analysis.

3. Task States and the Idle Task

https://www.instructables.com/FreeRTOS-With-Arduino-02-Task-Switching/

Figure 3.6: FreeRTOS Task State Machine

Unlike a Super-Loop where code is always "Running," a FreeRTOS task exists in one of four states:

  1. Running: The task is currently using the CPU.
  1. Ready: The task is prepared to run but is waiting for a higher-priority task to finish.
  1. Blocked: The task is waiting for an event (e.g., waiting 10 seconds for the next GPS update).
  1. Suspended: The task is completely paused by the programmer.

3.1.3 Advantages of Multithreading in IoT Tracking Systems

In the domain of Internet of Things (IoT) and remote telemetry, the ability to handle multiple asynchronous events is the boundary between a prototype and a production-grade device. By implementing a multithreaded architecture on the ESP32-S3, the Nano Tracker moves beyond the limitations of linear execution, offering several mission-critical advantages.

1. Elimination of "Blocking" Latency

In a standard single-threaded application, the system is only as fast as its slowest component. The SIM800L GSM module is inherently slow due to its reliance on cellular handshakes and TCP/IP protocol timings. A single AT+HTTPACTION command can take upwards of 15 seconds to return a response if the network is congested.

  • Multithreaded Solution: In our FreeRTOS-based firmware, these "blocking" periods only pause the GSM Task. Because this task is isolated on Core 0, the GPS Task on Core 1 continues to parse satellite data at a high frequency.
  • Result: The tracker maintains a "Zero-Drop" policy for incoming coordinates, ensuring the movement path is smooth and accurate on the Traccar map.

2. High-Precision Timing and Determinism

Tracking a moving asset requires precise interval logging. If a tracker is set to log data every 10 seconds, but the CPU is busy trying to reconnect to a cell tower, that 10-second interval might stretch to 40 seconds. This "jitter" ruins the data quality for speed calculations and geofencing.

  • The RTOS Advantage: Multithreading allows us to assign a Fixed Priority to the sensing task. The FreeRTOS scheduler ensures that the sensing task gets the CPU "slices" it needs exactly when it needs them, regardless of what the GSM module is doing. This creates a Deterministic System where data sampling occurs with microsecond precision.

3. Decoupling Data Acquisition from Transmission

One of the most advanced features of this project is the separation of Data Logic from Network Logic. This is achieved through "Task Decoupling" using FreeRTOS Queues.

  • Asynchronous Flow: The GPS task produces data at a rate of 1Hz (1 update per second). The GSM task consumes data at a rate of 0.1Hz (1 update every 10 seconds).
  • The Buffer Benefit: By using an inter-task queue, the GPS task can "post" its latest coordinates to a shared memory space and immediately return to its sensing duties. The GSM task picks up the most recent data whenever the network is ready. This prevents the slow "Upload" speed from bottlenecking the fast "Sensing" speed.

4. Fault Tolerance and System Resilience

In remote IoT devices, software hangs are common due to signal interference or hardware noise. In a Super-Loop, if the GSM code enters an infinite loop while waiting for a response, the entire device dies.

  • Isolated Failure: In a multithreaded system, if the GSM Task crashes or enters a "Blocked" state indefinitely, the GPS and Motion tasks continue to function.
  • Watchdog Integration: We can implement a "Watchdog Timer" (WDT) specifically for the GSM task. If the GSM task doesn't "check in" within 60 seconds, the system can kill and restart just that specific task without rebooting the whole device, preserving the GPS fix and uptime.

5. Efficient Power Management via "Tickless Idle"

Multithreading allows the ESP32-S3 to identify periods where no tasks are ready to run. In a standard loop, the CPU is always running at 240MHz, even if it’s just doing a delay().

  • The RTOS Sleep: When both the GPS and GSM tasks are in a "Blocked" state (e.g., waiting for their next timer), FreeRTOS automatically enters the Idle Task. We can configure this task to lower the CPU frequency or enter Light Sleep. The device only wakes up when a Task is ready or an interrupt (like the MPU-6050 motion trigger) occurs.

3.1.4 Dual-Core Processing: Distributing Load between Core 0 and Core 1

The ESP32-S3 is a dual-core System-on-Chip (SoC) featuring two power-efficient, high-performance Xtensa® 32-bit LX7 microprocessors. In a traditional "Super-Loop" architecture, the second core often remains idle, effectively wasting about 50% of the available computational power. In this project, we implement asymmetric task distribution to run key workloads in parallel and eliminate the main bottlenecks of GPS tracking.

1) Hardware anatomy: PRO_CPU vs. APP_CPU

Within the ESP32-S3, the two cores are internally designated by the framework as:

  • PRO_CPU (Core 0) — Protocol / networking core
    • Optimized for networking stacks and high-latency communication.
    • In our system, TaskGSM is pinned to Core 0.
    • Cellular handshakes (waiting for tower responses) happen here, so these delays do not block sensor reads or the system timing.
  • APP_CPU (Core 1) — Application / user logic core
    • Used for user-defined, time-sensitive processing.
    • In our system, TaskGPS is pinned to Core 1.
    • This core focuses on fast character-by-character parsing of NMEA strings from the u-blox NEO-8M.

2) Manual task pinning: xTaskCreatePinnedToCore()

Standard FreeRTOS uses xTaskCreate(), which allows the scheduler to move tasks between cores dynamically. While efficient for general computing, this can be risky in a GPS tracker because task migration may add small delays known as context switching overhead.

To improve stability, we use xTaskCreatePinnedToCore(), which pins each task to a specific core. This helps ensure:

  1. Cache locality
    • The GPS task keeps its working data in the same core’s local cache, improving execution speed.
  1. Interrupt isolation
    • GPS UART interrupts wake Core 1.
    • GSM UART interrupts wake Core 0.
    • This reduces contention for CPU cycles.

3) Solving the shared-resource conflict

A major challenge in dual-core systems is the race condition. Both Core 0 and Core 1 share the same internal SRAM. If Core 1 writes a new GPS coordinate at the same moment Core 0 reads it for transmission, the data can become corrupted.

Solution: Inter-Processor Communication (IPC)

Instead of using global variables (not thread-safe), our firmware uses FreeRTOS queues:

  • Core 1 pushes the latest GPS data into the queue.
  • The queue mechanism briefly locks memory to guarantee Core 0 receives a clean copy.

4) Thermal and power efficiency through load balancing

Running a single core at 240 MHz can generate heat inside a compact, unventilated enclosure. By distributing work across both cores:

  • Both cores can run at a lower frequency (for example, 160 MHz) while achieving better overall performance.
  • Heat is spread across the silicon die, reducing hot spots and improving long-term reliability.
  • Average current draw can be reduced because tasks complete in bursts, then enter a blocked (sleep) state.

3.2 Task Management and Prioritization

3.2.1 Task 1 (Sensing): High-Priority GPS Stream Processing

The Sensing Task is the primary data producer of the system. In our FreeRTOS architecture, this task is pinned to Core 1 (APP_CPU) and assigned Priority 2. Its sole responsibility is to maintain a "clean" and "lossless" ingestion of NMEA sentences from the NEO-8M module.
1. High-Frequency UART Ingestion
The NEO-8M transmits data at 9600 bits per second (baud). While this seems slow, the GPS module sends a burst of data every second containing multiple sentences ($GPRMC, $GPVTG, $GPGGA, etc.).
• The Challenge: If the CPU is distracted for even 100 milliseconds, the UART hardware buffer will overflow, causing a "Frame Error."
• The Solution: Our Task 1 uses an interrupt-safe while(gpsSerial.available()) loop. This ensures that the task spends the majority of its CPU "slices" emptying the hardware buffer and moving the data into the TinyGPS++ object.
2. NMEA 0183 Parsing and Checksum Validation
Not all data from the GPS is valid. Signals can be corrupted by electromagnetic interference (EMI) from the ESP32’s own WiFi radio. Task 1 performs a background Checksum Validation.
• Each NMEA sentence ends with a * followed by a Hexadecimal value.
• TinyGPS++ calculates the XOR sum of the characters in the task and compares it to the Hex value.
• If they don't match, the data is discarded. This ensures that the tracker never sends "garbage" coordinates (like 0.0, 0.0) to the Traccar server.
3. Geodetic Calculations and Formatting
Once a "Valid Fix" is confirmed, Task 1 converts raw GPS data into a structured format.
• Coordinate Precision: Latitude and Longitude are stored as double (64-bit) variables to maintain accuracy within 1 meter.
• Unit Conversion: Raw knots are converted to $km/h$, and the altitude is calculated relative to the WGS84 ellipsoid.

3.2.2 Task 2 (Communication): Low-Priority GSM/GPRS Stack

The Communication Task is the system's "Data Consumer." It is pinned to Core 0 (PRO_CPU) and assigned Priority 1. This task is architected to handle the slow, high-latency nature of cellular networks without crashing the device.

1. The AT Command State Machine

Unlike the GPS task, which just "listens," the GSM task must engage in a complex "dialogue" with the SIM800L. Every interaction follows a strict state machine:

  1. Command State: Sending AT+HTTPACTION=0.
  1. Wait State: The task enters a Blocked state using vTaskDelay(), allowing Core 0 to handle internal background tasks while waiting for the network.
  1. Verification State: Parsing the response to check for the +HTTPACTION: 0,200 success code.

2. GPRS Attachment and Bearer Management

The GSM task manages the "Bearer Profile." This is the virtual tunnel between the SIM800L and the Internet.

  • Persistence: If the bearer fails (due to a tunnel drop in a basement or tunnel), Task 2 is programmed with an Auto-Reconnect Algorithm.
  • Sequence: It executes AT+SAPBR=0,1 (Close) followed by AT+SAPBR=1,1 (Open) to refresh the IP address provided by the carrier (Vodafone/Orange/WE).

3. URL Serialization and HTTP Post

Task 2 is responsible for "Data Packaging." It takes the coordinates from the Queue and wraps them into an OsMand Protocol URL string.

  • String Management: Since URLs can be long, Task 2 utilizes a large stack allocation (10KB) to prevent crashes during the concatenation of Latitude, Longitude, and Device ID strings.
  • Termination: It ensures AT+HTTPTERM is called after every session to prevent the SIM800L’s internal memory from leaking.
